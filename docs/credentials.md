# Конфигурация и credentials Aenea

## Принятое соглашение

Хранилище проекта — Proton Pass, vault **`aenea`**. Item называется по сервису, поля — по назначению. Это отдельное соглашение Aenea; хранилища и профили ICA/Codex не используются.

Текущий профиль — `dev`, выбирается явно через локальный reference-файл `.env` с `AENEA_ENV=dev`. В `.env` хранятся только `pass://` ссылки и несекретные настройки. Версионируемый `.env.example` содержит тот же шаблон. Значения секретов пользователь добавляет самостоятельно в Proton Pass, не в Git и не в чат.

В этом шаге записи Proton Pass не создавались, не читались и не проверялись. Пути ниже — согласованная адресация для настройки. Наличие ссылок в файле не доказывает наличие соответствующих item/полей или доступ к ним.

## Reference-профиль dev

| Переменная процесса | Ссылка или несекретное значение | Назначение |
| --- | --- | --- |
| `AENEA_ENV` | `dev` | Явный выбор окружения. |
| `AENEA_SQLITE_PATH` | `runtime/aenea.dev.sqlite3` | Проектный путь SQLite, пока без реализованного загрузчика. |
| `LANGFUSE_BASE_URL` | `pass://aenea/langfuse/base_url` | Адрес hosted Langfuse именно выбранного проекта/региона. |
| `LANGFUSE_PUBLIC_KEY` | `pass://aenea/langfuse/public_key` | Публичный API-ключ проекта Langfuse. |
| `LANGFUSE_SECRET_KEY` | `pass://aenea/langfuse/secret` | Секретный API-ключ того же проекта Langfuse. |
| `OPENAI_API_KEY` | `pass://aenea/openai/api_key` | Ключ Aenea; отдельный профиль RaidSL передаёт его как `RAIDSL_API_KEY`. |
| `TELEGRAM_API_ID` | `pass://aenea/telegram/api_id` | ID собственного Telegram application. |
| `TELEGRAM_API_HASH` | `pass://aenea/telegram/api_hash` | Hash того же application. |
| `TELEGRAM_PHONE` | `pass://aenea/telegram/phone` | Номер отдельного аккаунта; нужен только для login. |
| `TELEGRAM_SESSION` | `pass://aenea/telegram-session/secret` | StringSession; отдельный reader-профиль после login. |

`base_url` не является секретом, но хранится рядом с ключами, чтобы явно выбирать один hosted-проект. Например, EU Cloud использует `https://cloud.langfuse.com`, US — `https://us.cloud.langfuse.com`; фактический адрес берётся из выбранного проекта, а не угадывается по местоположению пользователя. [Настройка Langfuse](https://langfuse.com/docs/observability/get-started).

Ссылки по именам требуют отсутствия неоднозначных vault/item. Если имя переименовано, ссылка не разрешается или недоступна — запуск блокируется. Автоматического перехода к другому item, аккаунту или хранилищу нет. Переход на ссылки с точными ID при необходимости выполняется явно, без чтения значений в вывод.

## Инъекция в процесс

Используется native `pass-cli run` с явным `--env-file`. Полный профиль требует заполнения всех ссылок; для Reader используются [отдельные Telegram-профили](telegram-reader.md):

```sh
pass-cli run --env-file .env -- uv run --locked --package aenea-telegram-agent aenea-telegram
```

Все активные ссылки выбранного файла должны разрешаться. Готовность полного профиля не проверялась; наличие ссылок не доказывает готовность credentials. Перед отдельными проверками сервисов следует явно подготовить reference-профиль только с нужными ссылками; отсутствие доступа нельзя маскировать fallback-механизмом.

RaidSL использует `configs/raidsl/dev.openai.env.example` либо
`configs/raidsl/dev.packet.env.example` с явным провайдером и `AENEA_ENV=dev`.
`RAIDSL_API_KEY` ссылается соответственно на `pass://aenea/openai/api_key` или
`pass://aenea/deepseek/api_key`. Смена провайдера явная, без fallback при ошибке.
Пользователь подготовил ключи самостоятельно; PR3 проверяет их только через
инъекцию в процесс для синтетического demo, без печати значений или создания item.

Не выполнять `source .env`: shell не разыменовывает Proton-ссылки. Не материализовывать `.env` с plaintext-секретами, не использовать `pass-cli inject` для генерации такого файла, не выводить окружение процесса. Сохранить стандартное маскирование CLI. Приложение получает уже разрешённые значения через окружение, без собственного загрузчика секретов и неявного dotenv fallback.

CLI не загружают `.env` самостоятельно. Reader и отдельный RaidSL demo проверяют
уже разрешённые переменные процесса. Offline-проверки и тесты выполняются обычным
`uv` без credentials; Langfuse пока не подключён.

## Telegram-сессия

Согласовано хранение Telethon StringSession в Proton Pass vault `aenea`, item `telegram-session`, hidden-поле `secret`. Явная команда `login` создаёт item через native `pass-cli` с JSON stdin. Существующая запись не перезаписывается. Повторные запуски получают сессию через native `pass-cli run` и отдельный reader-профиль. Сессия и entity cache существуют только в памяти, локального session-файла нет. Восстановление и ограничения обновления описаны в [руководстве Reader](telegram-reader.md).

Файлы сессий и локальные SQLite игнорируются Git, но Reader не создаёт session-файлов. В доменную SQLite или hosted Langfuse содержимое сессии не попадает. Доступ и резервное хранение секрета обеспечиваются Proton Pass; `.gitignore` не заменяет защиту хранилища. Коды входа и 2FA не передаются через чат или аргументы команд.

## Правила

- Не печатать секреты, не помещать их литералы в аргументы команд, Git, логи и тестовые данные.
- Не читать vault `Personal` и не использовать `ica` или инфраструктурный vault Codex как fallback.
- Не менять глобальные defaults CLI; всегда задавать reference-файл и проектное окружение явно.
- Не создавать, не импортировать, не мигрировать, не удалять и не ротировать credentials как побочный эффект запуска.
- При отсутствии поля или доступа остановить соответствующую authenticated-операцию и сообщить о блокере.
- `.env` остаётся локальным и игнорируется Git; `.env.example` разрешён в Git только со ссылками и несекретными настройками.
